** check the keys

- For ssh file transfer, salsa requires a valid ssh-key.  If expired,
  generate a new one

  #+begin_src bash :results nil
ssh-keygen -t ed25519 -C "an identifying comment"
  #+end_src

  for =~.ssh=.  To ease recognition, assign a good name; to protect
  assign a password; copy the public key of the pair (=my_key.pub=) to
  salsa.
- While one may use ssh-keys to sign commits to git, =debsign= only
  accepts GPG keys.
- Any upload by =dput mentors example.changes= requires
  =example.changes= to be signed by a recognized GPG key.  If expired,
  generate a new one

  #+begin_src bash :results nil
gpg --full-generate-key
  #+end_src

  with a password, a date of expiration, and a revocation.  Export the
  public part

  #+begin_src bash :results nil
gpg --armor --export <GPG KEY ID>
  #+end_src

  for an eventual copy to the mentors page.
- Either ssh key or GPG key may be used to sign commits.  Similar to
  GitHub, if the public keys of the corresponding key pair is known to
  salsa, there will be a green check mark next to the commit.
- Don't edit the (optional) comment of a ssh key pair; create a new
  one instead.
- The date of expiration of a GPG key equally enters into the
  computation of the key pair.  While the /fingerprint/ of a GPG key
  isn't affected by, e.g., an extension, by diffview changes of
  /sections/ of public keys become visible.  Since e.g., Salsa does
  not accept two key pairs of identical fingerprint, the elder would
  need to be /deleted/.

  Since /deletion/ of a key renders all commits signed with it to
  salsa's inspection "signed, but with an unknown key", it generally
  is better to use GPG keys with a date of expiration set, and if
  necessary, to revoke a key.  Then "old keys" no longer in active
  (signing) use still serve as check reference.
- If one opts-in into 2FA, User settings -> Access -> Personal access
  tokens allows to define additional passwords to successfully fetch
  from, and push to the salsa hosted repositories via the CLI if their
  scope is includes both =read_repository= and =write_repository=.
  They are monitored (report includes life time, time and IP of most
  recent use) in the same directory.

** check local git

Settings usually / globally used may interfere with the update.  E.g.,
if =DEBEMAIL= defined in =~/.bashrc= differs from the one on line
=Maintainer:= in file =debian/control=, a call like =dca -i= does not
create =0.15.0-1= but =0.15.0-1.1=, where the trailing =.1=, or =.2=,
etc. is indicative for a non-maintainer upload (NMU).  While not wrong
in the working of the package to provide, =lintian= will request a
justification for a NMU instead of one by the maintainer known so far.

- There is no need to overwrite =.gitrc= for good as changes to git may be
  introduced per project by a flag =--local=.

  To check run

  #+begin_src bash :results nil
  git config --local -l
  #+end_src

  Else define / overwrite in pattern of

  #+begin_src bash :results nil
  git config --local core.editor "vim"
  git config --local merge.tool "kdiff3"
  git config --local user.name "Pen Paper"
  git config --local user.email "pen@paper.com"

  # if commits are to be signed with a GPG key:
  git config --local user.signingkey 1234ABCD1234ABCD
  git config --local gpg.format openpgp

  # if commits are to be signed with a ssh key:
  git config --local user.signingkey ~/.ssh/special_ssh_ed25519.pub
  git config --local gpg.format ssh
  #+end_src

- At present ([2026-09-17 Thu]), the Python implementation of =comitizen= (version
  4.18.1) is found compatible to the automatic signing, i.e.

  #+begin_src bash :results nil
  git config --local commit.gpgsign true
  #+end_src

  in presence of =ssh-askpass= (version 1:1.2.4.1-16+b1) -- a small widget opens
  to request the input of the password (presuming aside of =chmod= the ssh key is
  set up with this protection).  However the password has to be entered each
  time.
- Best to run a test commit (which anyway can be amended later).

- It might be necessary to build a .deb based on a particular (read:
  /not/ the most recently published) version of a gem distributed on
  rubygems.  To fetch and unpack this source, as well as to provide
  the .orig.tar.gz file eventually required for instance running
  =dkgp-buildpackage= (if this tarball can not be found elsewhere) the
  pattern of

  #+begin_src bash :results nil
gem fetch chef-utils --version 19.2.12
gem unpack chef-utils-19.2.12.gem
tar -caf ruby-chef-utils_19.2.12.orig.tar.gz chef-utils-19.2.12
  #+end_src

  can be useful, for instance to copy-paste the content of this
  rubygem into the package data /without/ assistance by =uscan= and
  =d/watch=.

** building

- The mentors page promptly raises an error if an upload does not
  provide the source =.dsc= files.  If absent, a package will not be
  admitted to the public section of the mentors page, too.  Though a
  subsequent upload is possible, it is simpler to provide all files at
  once (read =-si= like "sources included").

  #+begin_src bash :results nil
    dpkg-buildpackage -si
    cd ..
    debsign -k <key-id> example*.changes
    deput mentors example.changes
  #+end_src

- The mentors page is set for testing / incremental improvement.  If
  doing so, previous =example*.mentors.upload= will block an
  additional upload, so rename the log about the earlier upload if
  present / retained.

** difference update and backport

- The watch file (=debian/watch=), though still in syntax 4
  successfully notified the release of mdl, version 0.15.0.  Since it
  still functional -- which can be checked locally by

  #+begin_src bash :results nil
uscan --verbose --no-download
  #+end_src

  at any time, and given the difficulties about an update to syntax 5,
  it is retained in place.

- Update: clone the salsa repository
  - import a new tarball, to
    - update branch =upstream= with a new version (from the Rubygem
      repository)
    - update the branch =pristine-tar= both with the tarball as well
      as the delta files
    - the (initial merge) of the new upstream version into the default
      branch =master=.

        If "the three branches" are =master= (as the default branch),
        =upstream=, and =pristine-tar=, the commands in question are

        #+begin_src bash :results nil
    git checkout master
    uscan --download
    gbp import-orig --uscan --pristine-tar
    gbp dch --auto  # update of file debian/changelog
        #+end_src

        Multiple Debian Ruby Team managed packages however name their
        default branch =debian/latest= (instead of =master=),
        =upstream/latest= (instead of =upstream=), and =pristine-tar=.
        Then (with =uscan= version 2.26.9, and =gbp= 0.9.43) the three
        commands above are

        #+begin_src bash :results nil
          uscan --download
          gbp import-orig --uscan --pristine-tar \
             --upstream-branch="upstream/latest" \
             --debian-branch="debian/latest"
          gbp dch --auto --debian-branch="debian/latest"
        #+end_src

  - Notes the differences; command

    - =dch -i= /increments/ the version in the changelog
    - =dch -a= one /adds/ an another note about a modification of the
      package to be built within the same current version number which
      is marked with a new =*= "bullet point"
    - a =dch -e= merely opens an editor to manually edit the change log

    However note to remove any trailing whitespace in file
    =debian/changelog= which otherwise raises an issue in checks by
    =lintian=.

- Backport

  - Collect the .dsc and archives about the version already accepted to
    /testing/, for instance at
    https://packages.debian.org/source/forky/ruby-mdl
  - check-out the default branches =debian/latest=, =pristine-tar=, and
    =upstream/latest=
  - continue with the checkout of the branch to host the new backport, for
    instance =debian/trixie-backports=
  - update the content with achievements of branch /testing/ by

    #+begin_src bash :results nil
   git merge origin/debian/latest
    #+end_src

    This may create merge conflicts (resolve by assistance of =git mergetool=).
    Ensure file d/changelog tracks all previous edits leading up to the latest
    release /of to testing/ prior to the backport now under construction.
  - Announce the backport to d/changelog by =dch --bpo=.  Inspect d/changelog
    for correct email address; there should be no trailing whitespace -
    neither on lines, nor a final blank line.
  - Secure the state by

    #+begin_src bash :results nil
   git add debian/changelog
   git commit -m "Backport upstream version x.y.z." -sS
    #+end_src

    with an optional DCO and GPG signature (known to salsa and not yet
    expired).
  - Section /Packaging/ on [[https://backports.debian.org/Contribute/][backports.debian.org]] /recommends/ "to include in the
    changes file all changelog entries since the last version on
    debian-backports or since stable if it's the first version. You should do
    this by passing "-v" to dpkg-buildpackage. E.g.: "sbuild
    --debbuildopt='-v0.7.5-2'" or "debuild -v0.7.5-2", where "0.7.5-2" is the
    version in stable."

    Let's say the most recent version to /testing/ is =0.18.1+ds-2= is to be used
    to provide =0.18.1+ds-2~bpo13+1=.  On the [[https://tracker.debian.org/pkg/ruby-mdl][package tracker page]], identify the
    most recent version available to /stable-bpo/ (if absent, /stable/), for
    instance =0.17.0-2~bpo13+1=.  Then use ~-v=0.17.0-2~bpo13+1~ (no quotes, no
    spaces) as flag to recapitulate all changes since the most recent version
    published to /stable/ to the mentors page.  This is a readout for the
    reviewing sponsor, not an edit of d/changelog.)
  - Sign by =debsign -k 1234ABCD1234ABCD= and upload =dput mentors= on file
    .changes as usual.  The upload to the remote repository on salsa launches
    the CI (including the upstream testsuite).  Don't forget the tag (here
    =debian/0.18.1+ds-2_bpo13+1= since the tilde is not accepted) and file the
    RFS ticket.

** preparation of NMU packages

Lessons learnt around =ruby-chef-utils=:

- To eventually update a version =1.2.3= without updating source data,
  the new version increments to =1.2.3-1=, then =1.2.3-2=, etc.
- If a NMU includes a new upstream version, =1.2.3= is followed by
  =1.2.4-0.1= where =-0.1= then is the proper version indicator of a
  NMU.
- If investing for NMU because the usual maintainers don't come back
  in 2 to 4 weeks after notice, prioritize action on grave / release
  critical bugs.
- The intent of NMUs is to bring a package back to work (at all) with
  minimal changes.  Thus edits on function / style (e.g., adjust to
  current Debian policy), issues not already reported as (grave) bug
  are beyond the intent.  These can be tasks for a regular upload by
  the usual uploader / team maintainer.
- With the .dsc file of the previously accepted upload to Debain,
  after local building of the package, run e.g.

  #+begin_src bash :results nil
nmudiff --old --no-mutt --nondd
  #+end_src

  to provide a summary of the changes vs. the previous version, to be
  sent with a different mail program than mutt, with explicit
  indication to seek a sponsor for the eventual upload to Debian.  To
  send this to corresponding bug ticket(s) helps the sponsor, though
  again "the less changes, the better for the NMU".

** interaction with the new name space on salsa

The package now is within the namespace of the Debian Ruby Team.  The
interaction with the corresponding repository uses =ssh=, and to pull
from / push to the repository requires both =git= as well as
=ruby-gitlab=.  See its [[https://wiki.debian.org/Teams/Ruby/Packaging#Using_Git][Wiki]] with hints relevant to packaging, for
instance about

- how to check the connection to salsa via ssh

  #+begin_src bash :results nil
    ssh -vT git@salsa.debian.org
  #+end_src

- use of a stanza in =~/.ssh/config= (for security, protected by a
  =chmod 600=) for a more comfortable connection

  #+begin_src bash :results nil
    Host salsa.debian.org
        User git
        IdentityFile ~/.ssh/id_ed25519_my_key_for_salsa
        IdentitiesOnly yes
  #+end_src
